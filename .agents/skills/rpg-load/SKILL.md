# 加载与主持 RPG 本

从用户在 `$rpg-load` 后给出的本名或当前对话中确定要加载的本，以 GM 身份主持文字冒险。

## 定位本

- 优先使用当前工作区中同时含 `modules/README.md` 和 `core/rules.md` 的项目根目录。若当前目录是项目子目录，向上定位；也可从本 skill 目录向上三级找到所属项目。下文路径均相对此根目录。
- 本位于 `modules/<本名>/`，以实际存在的 `module.md` 为准。
- 本名未指定或找不到时，列出 `modules/` 下各个含 `module.md` 的子目录及其 `title`、`tone`、`rating`，让用户选择，等待答复后再开局。

## 读取本与存档

1. 读取 `modules/<本名>/module.md`，解析 frontmatter 和“文件”“规则覆盖”“开局”三节。
2. `engine: core` 时读取当前 `core/rules.md`；本明确声明的规则覆盖优先于 core 对应章节。`engine: none` 时使用本自带的规则，不自动套用 core 机制。
3. 读取清单中的设定、地图、事件、道具、角色卡和存档。声明的角色目录可包含多张卡，也可一文件包含多名角色。core 本缺少某一类内容时，按 `modules/README.md` 使用 `core/` 的相应通用模板或内容；不要把模板示例当成实际玩家进度。
4. 只读取当前本及其所需的项目规范和 core 文件，不加载其他本或 `.tower` 中无关的历史任务。

本 skill 主持的是聊天中的 Markdown 存档，默认使用清单声明的存档路径（通常为 `modules/<本名>/saves/save-state.md`）。Web 游戏的 `web/saves/<本名>/slot<N>.json` 是独立槽位；用户明确要求读取 Web 槽位时，先确认槽位和格式，再读取对应 JSON，不把两种存档混写。

## 开局或续档

- 存档与本的开局一致，且尚无行动进度、已触发事件或后续记录时，按“开局”写开场情境。常规初始状态为第 1 天 · 晨；本的时段覆盖优先。
- 已有进度时，用两三句话概括时间、地点、角色状态和进行中的进度钟，然后接着走；不只凭“第 1 天 · 晨、事件为空”判断为新游戏。
- 存档缺失时按开局和玩家卡建立初始状态；已有存档不重置。信息互相矛盾且影响继续游戏时，只澄清必要的冲突。

## 主持与真实掷骰

- core 本按 §0 的“宣言 → 判定 → 叙述 → 结算”推进。先说明难度、风险和耗时；只有结果不确定且失败有意义时掷骰。一条聊天消息不等于一个时段。
- 需要骰子时调用可用的 shell 真实掷骰，并展示骰面、保留的骰子、加值来源、总值、难度和结果档位。每颗骰独立抽样，允许重复点数；不要编造结果。
- Windows PowerShell 掷 2d6：

  ```powershell
  1..2 | ForEach-Object { Get-Random -Minimum 1 -Maximum 7 }
  ```

- 跨平台 Node.js 掷 2d6（仅使用标准库）：

  ```sh
  node -e "const {randomInt}=require('node:crypto'); console.log(JSON.stringify([randomInt(1,7),randomInt(1,7)]))"
  ```

- 掷 1d6 时只生成一颗；优势 / 劣势生成三颗后按规则保留两颗。d66 生成两颗独立 d6，第一颗为十位、第二颗为个位，不把它当作 1–66 的连续整数。
- 每个实际消耗的时段结束时按 core §4.2 做事件判定，再用本指定的事件表抽事件；本有地点 d20 等明确覆盖时按覆盖执行。0 耗时不抽事件，多时段行动逐时段处理。
- 叙述使用第二人称或玩家选择的视角，NPC 按角色卡的动机和秘密行动，内容遵守本的 `rating` 与基调。
- 每段叙述结束后给出 2–4 个可选行动，玩家也可以自行声明其他行动。

## 存档

- 每个时段结束或玩家要求“存档”时，用可用的文件编辑工具更新当前存档。记录时间、地点、资源、物品、关系、进度钟、事件、线索和必要的 GM 备忘。
- 保存后重新读取，确认结算结果已写入，未丢失既有进度。不要向玩家展示标为“玩家不可见”的 GM 备忘。
- 默认只改当前本的存档；修改本的其他内容、`core/` 或 Web JSON 槽位须来自用户相应的明确要求。
